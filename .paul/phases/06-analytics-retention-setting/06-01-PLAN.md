<objective>
## Goal
An administrator sets **Remove search analytics older than X days** (default **365**) in the Xperience
administration, and the existing `XpSearch.QueryLogRetention` scheduled task honours it — deleting
query-log rows and the answered (accepted/dismissed) popularity + synonym suggestion rows that are older
than the cutoff. The code-level `RetentionDays` option stops being the source of truth.

## Purpose
Search analytics is the one table in the product that grows without bound on every host, and today the
only knob is a C# option nobody edits after go-live. Xperience's own answer for the same problem is a
Settings-app value ("Delete contacts who have not been active for the last X days"); the library should
look identical to an admin. This must ship before Phase 5 tags v1.0.0 so the default and the setting are
in the release, not a breaking follow-up.

## Output
- Unit spec `docs/internal/units/AR-1.md` (Fable-authored, committed with the unit — per the
  spec → implement → review loop)
- Settings surface seeded idempotently by the analytics installer, retention task reading it, broader
  prune, tests, guide/ADR/CHANGELOG/KNOWN-LIMITATIONS updates, host-pass checklist section
- Merged to `main`, pushed, host rebuilt; owner walks the new checklist items
</objective>

## Research already done (2026-09-02)
- Kentico docs: `ISettingsService[codeName]` returns string; `IConversionService.GetInteger(value, fallback)`
  casts. `IInfoProvider<SettingsKeyInfo>` is public. The docs' "custom settings" guide builds a custom
  module + UI pages rather than inserting into the built-in **Settings** application; no docs page
  confirms or denies that code-created `SettingsCategoryInfo` + `SettingsKeyInfo` rows render there.
  → Task 2 spikes the Settings app FIRST (it is what the owner asked for) with a defined fallback.
- Kentico's inactive-contact deletion: Settings → Digital marketing → Contact management,
  "Delete contacts who have not been active for the last X days", minimum 7. Mirror the wording shape.
- Existing task already registered by attribute (`XpSearch.QueryLogRetention`), configured manually in
  Scheduled tasks (ADR-0015); `RetentionBatchSize` stays a code option. Popularity/synonym suggestion
  stores keep every human-answered row forever (`ReplaceAsync` only rewrites pending rows) — that is
  the second unbounded growth and the honest extra prune.

## AC-1: Settings are visible and editable in the administration
```gherkin
Given a host that called AddXpSearch and has started once
When an administrator opens Search ingestion -> Settings in the Xperience administration
Then every global XpSearchOptions / Analytics value is listed (retention shows 365),
  saving a valid value persists and applies without a restart; out-of-range values are rejected
```

## AC-0 (owner amendment 2026-09-02): All global options load through ConfigureOptions
```gherkin
Given a host whose AddXpSearch lambda sets MaxPageSize = 50 and a stored settings row with 80
When XpSearchOptions is resolved
Then MaxPageSize is 80 (stored row wins), and with no stored row it is 50 (lambda stands)
```

## AC-2: Retention task honours the setting
```gherkin
Given the setting is 30 and query-log rows exist at 10, 29, 31 and 400 days old
When XpSearch.QueryLogRetention runs
Then only the 31- and 400-day rows are deleted and the task result reports the count and cutoff
```

## AC-3: Answered suggestions are pruned, pending ones are not
```gherkin
Given accepted/dismissed popularity and synonym suggestion rows older than the cutoff,
  plus pending rows older than the cutoff and answered rows newer than it
When the retention task runs
Then only the old answered rows are deleted; pending rows and newer answered rows remain
```

## AC-4: Missing or unreadable setting falls back safely
```gherkin
Given the settings row is absent or holds a non-integer value
When the retention task runs
Then it uses 365 days, logs a warning naming the setting, and still completes
```

## AC-5: Seeding is idempotent and upgrade-safe
```gherkin
Given a host that already has the setting at a custom value
When the application restarts (installer runs again)
Then the value is untouched and no duplicate category/key is created
```
