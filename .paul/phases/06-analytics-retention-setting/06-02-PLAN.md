<objective>
## Goal
Every value that 06-01 made editable globally is edited **per index**: `IOptionsMonitor<XpSearchIndexSettings>.Get(indexCodeName)` returns that index's settings (stored row over code defaults), a save on one index rebuilds only that index's instance, and the retention and popularity tasks apply each index's own numbers. The global Settings page and the global row go away.

## Purpose
Owner decision at the 06-01 checkpoint (2026-09-03): "add the settings per index instead, using named options". Every one of the sixteen values is meaningful per index (cache lifetime, page sizes, suggestion limits, retention window, mining windows), each request names exactly one index, and named options cache one instance per name — the shape fits without a global layer. It also lines up with how popularity boosts and typo tolerance are already per index.

## Output
- Unit spec `docs/internal/units/AR-2.md` (Fable-authored)
- Named options type + `IConfigureNamedOptions` overlay + per-name invalidation in Core; row class gains an index-name column; consumers call `Get(index)`; tasks per index
- `Search settings` page under each index's tuning section (`XpSearch.Admin`); global page deleted
- Tests, docs, CHANGELOG (06-01's Unreleased entries **rewritten**, not appended), checklist §Y
- Merged, pushed, host rebuilt; owner walks §Y
</objective>

## Facts established while planning (2026-09-03)
- Names: index code names are sanitised by the admin's code-name component (no spaces/invalid chars). Only **case** can differ between a request's `index` and the registered name; `IOptionsMonitor.Get(name)` is ordinal. Key by the registered name (`ILuceneIndexAccessor` / `ILuceneIndexManager.GetAllIndices()` matched OrdinalIgnoreCase), never by the raw request string.
- Per-name invalidation: drop `XpSearchSettingsChangeTokenSource`; the row's `Insert/Update/Delete.After` events call `IOptionsMonitorCache<XpSearchIndexSettings>.TryRemove(row.IndexName)`. `OptionsMonitor.Get(name)` re-runs the named configure on the next read of that name only.
- Multiple indexes at once is the normal case and the reason named options fit: one cached instance per name, no cross-talk.
- `CachedSearchPipeline` reads `MaxQueryLength`/`CacheTtl` before the index is validated; it needs the registered name first (cheap: the accessor's registry is in memory).
- The popularity task already groups rows by index name; the retention task will iterate registered indexes and prune orphan rows (index no longer registered) with the code defaults.
- 06-01 was never released (pre-1.0, Unreleased): the global row is dropped by the installer (rows with an empty index name deleted), no migration UI.

## AC-1: Named options per index over code defaults
```gherkin
Given a host lambda with MaxPageSize = 50 and a stored row for index A with 80 and no row for index B
When XpSearchIndexSettings is resolved for A and for B
Then A.MaxPageSize is 80 and B.MaxPageSize is 50, and requesting "a" (different case) yields A's values
```

## AC-2: A save on one index invalidates only that index
```gherkin
Given resolved settings for A and B
When A's row is saved with a new value
Then the next Get("A") carries the new value without a restart and Get("B") is unchanged (and was not rebuilt)
```

## AC-3: Search settings page in each index's tuning section
```gherkin
Given an administrator opens Lucene Search → an index → Search settings
When they change a value (within validation) and save
Then that index's row is created or updated; the global Settings page no longer exists under Search ingestion
```

## AC-4: Retention per index
```gherkin
Given index A retention 1 and index B retention 365, with old rows for both
When XpSearch.QueryLogRetention runs
Then A's old query-log/answered-suggestion rows are deleted and B's are kept; Last result reports per-index counts; rows of an unregistered index are pruned with the code defaults
```

## AC-5: Pipeline and tasks read the request's index settings
```gherkin
Given index A DefaultPageSize 3 and index B DefaultPageSize 20
When a query without pageSize hits A and then B
Then the responses report pageSize 3 and 20 respectively; the popularity task uses each index's lookback/limits
```
