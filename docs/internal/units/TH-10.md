# Unit TH-10 — Readable specificity: widget-scoped design rules, one triple for the reset

Owner 2026-09-03 (after TH-7): "why is the specificity `.xps.xps.xps`, should it be targeting
individual control names such as `.xps.xps-pagination`?" Decided compromise:

- **Design rules are scoped per widget block:** every default-theme rule for a widget is written
  under `.xps.xps-<block>` (root class + the block's own class), e.g.
  `.xps.xps-pagination .xps-pagination__link`, `.xps.xps-results .xps-results__empty`,
  `.xps.xps-suggestions .xps-suggestions__option--recent`. That is (0,3,0) with the child class —
  the same weight TH-7 ships today — and it reads as what it is. Rules on the block itself
  (`.xps.xps-pagination`) are (0,2,0): give them the weight they need by targeting the block's
  own child wrapper if one exists, or by the reset already covering the property; if a real host
  rule at (0,2,1) can reach a block-level property, keep that single rule at `.xps.xps-<block>.xps-<block>`
  and list it in the report (expect very few).
- **The element reset keeps ONE triple**, in one file (`default/_root.scss`): `.xps.xps.xps *`,
  `.xps.xps.xps :is(button, input, …)` etc. — a reset has no child class to hang weight on, so
  the repeated class stays there, documented in MARKUP.md and theming.md as "the one idiom".
- Shared design mixins (`_boxes.scss` emissions, `.xps-button`, `.xps-chip`, `.xps-highlight`,
  `.xps-sr-only` …) that are used by several widgets: scope them under the root + the element's
  own class doubled (`.xps .xps-button.xps-button`) so they stay (0,3,0) without naming a widget,
  OR emit them inside each widget's block scope — pick the one that keeps the compiled CSS
  smallest and say which.
