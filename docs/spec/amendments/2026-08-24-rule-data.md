# Spec amendment — `SearchResponse.ruleData` (ACCEPTED)

- **Status:** accepted — owner approval 2026-08-24; implemented by unit CR-4a
- **Date:** 2026-08-24
- **Amends:** §4.2 (`SearchResponse`), §8.2 (what a relevance rule can do)
- **ADR:** [ADR-0022](../../adr/0022-if-then-rule-engine.md)

## §4.2 — `SearchResponse` gains one optional member

```jsonc
{
  "results": [ /* ... */ ],
  "page": 1,
  "pageSize": 20,
  "total": 46,
  "totalPages": 3,
  "tookMs": 14,
  "redirect": null,
  "ruleData": {                    // OPTIONAL — new
    "banner": "espresso-week",
    "layout": "grid"
  },
  "queryId": "generated-guid"
}
```

`ruleData` is an **open object** (`additionalProperties: true`): editor-authored data attached by
matching Search-tuning rules — the *Return custom data* consequence — shallow-merged in rule order,
so a later rule wins a key it shares with an earlier one. It is **absent** — not `null`, not `{}` —
when no matching rule returned data.

Two properties come with it:

- the values are whatever a marketer typed into the rule form, so a client treats them as untrusted
  input, exactly as it treats `attributes`;
- a rule whose payload is not a JSON object is skipped, so one bad rule cannot corrupt the member or
  fail the search.

## §8.2 — the rule consequences

The list of what a rule can do becomes: pin, hide, boost, bury, filter the results, remove a word,
replace a word, replace the query, redirect, return custom data. The model behind it — N conditions,
N consequences per rule — is [ADR-0022](../../adr/0022-if-then-rule-engine.md).

## Versioning

Additive and optional: a client that ignores `ruleData` behaves exactly as before. This is a
**minor** version of both packages. `X-XpSearch-Api-Version` carries the semver *major*
(ADR-0006 decision 3) and stays at `1`.

The C# reshape of `XpSearch.Core.Tuning.TuningRule` that comes with it is a **major** event for the
package, but not for the wire contract: it is a server-side extension point (`IRelevanceTuningSource`),
not a payload.
